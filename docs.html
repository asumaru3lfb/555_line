目的

何のためのシステムか

「大洲カンパニー」は、大洲市の関係人口づくりプロジェクト「OZU555」の入口となる公式LINEアカウント。友だち追加した人に対して、6問のあいさつラリーで興味・関係性・お住まい・関わり方の希望を聞き取り、以後はリッチメニュー経由でまちの情報・関わり方の入口を提供する。

全体構成

3つの構成要素

要素役割実体
LINE公式アカウントユーザーとの唯一の接点。友だち追加／メッセージ／postback／リッチメニュー表示LINE Developers（チャンネルID 2011331444）
Bot本体Webhookを受けて会話ロジックを実行し、LINE Messaging APIで返信するCloudflare Workers（ozu555-line-worker）
会員台帳会員の状態・回答内容・イベント履歴を保存Cloudflare D1（SQLite）
ファイル置き場リッチメニュー画像・Webhookの取りこぼしデータの一時保管Cloudflare R2

運用主体は一般社団法人キタ・マネジメント（KM／三好）。Bot実装はバリューマネジメント（VM／丸岡さん）と共同。

処理の流れ

リクエストのライフサイクル

  1. LINEプラットフォームがユーザー操作（メッセージ／postback／友だち追加）をWebhookとしてWorkerに送信
  2. Worker（worker.js）が署名（LINE_CHANNEL_SECRET）を検証
  3. イベント種別に応じて core.js のハンドラーに振り分け（handleFollow / handleMessage / handlePostback）
  4. 回答内容は kernel.js の許可リスト（ALLOWED）を通過したものだけを member_events に追記し、対応するテーブル（members / member_attributes / member_referrals 等）を更新
  5. LINE Messaging APIで返信（reply）。reply tokenが失効している場合はpush APIにフォールバック
  6. 処理できない内容・想定外のエラーは事務局へ内部通知（現状ログのみ、メール送信は未設定）
設計方針

重視していること

  • 個人情報を集めすぎない：本名・住所・電話番号は聞かない。ニックネームのみで参加可能。
  • 特定情報と統計情報を物理的に分離：削除依頼が来たときに、必要な範囲だけを確実に消せるようにする（詳細は「データベース設計書」）。
  • 冪等性：LINEプラットフォームからの再送信（重複Webhook）があっても、同じイベントを二重に記録しない（idempotency_key）。
  • 自由記述の最小化：ユーザーの自由記述はkernelの許可リストにより、イベントログ本体には残らず、専用テーブル（member_referrals）にのみ書き込まれる構造にしている。
設計思想

5層＋αに分ける理由

「消してほしい」という依頼が来たときに、必要な部分だけを確実に消せるようにするため、集める情報の性質ごとにテーブルを分けている。特に本人を特定できる情報（氏名・第三者の名前など）と、統計的な属性情報を、はっきり別の場所に保管するのが設計の核。

core
members会員マスタ
LINEユーザーID・友だち追加日・退会日・pending_intake（入力待ち状態）を持つ土台テーブル。氏名等のPIIはここには置かない。
①
member_pii個人特定情報
表示名（ニックネーム）・メールアドレスのみ。削除依頼時は最優先でここを消す。
②
member_attributes非PII属性
推し・大洲との関係・お住まい区分/詳細（都道府県・市町）を保持。単体では個人を特定しにくい属性情報。
③
member_referrals第三者情報
紹介者のお名前など、本人以外の名前が入り得る自由記述。member_piiとは別枠にして削除範囲を明確に区切っている。
④
member_tags複数選択タグ
関わり方の希望（手伝う・学ぶ・あそぶ・応援する・住む等）を複数保持できるタグテーブル。source列で取得経路（rallyなど）を記録。
⑤
member_events追記専用ログ
「いつ・何をしたか」を追記するだけのログ。idempotency_keyで二重記録を防止。payloadはkernel.jsのALLOWEDリストを通過した値のみ格納可（自由記述は構造的に入らない）。

members.pending_intake について

あいさつラリー終盤の「紹介者名（自由入力）」を待っている間だけ立てる一時フラグ。CHECK制約で 'referrer_note' または NULL のみ許可。回答を受け取るかスキップされると即座にNULLへ戻す。

エラーが起きた際の対策

Webhookは届くがDBに何も書き込まれない

症状メッセージを送っても既読にならず、返信も来ない。

原因①LINE Official Account Managerの「チャット」機能がONになっていると、メッセージがWebhookより先にチャット機能に横取りされる。

対策①manager.line.bizで「チャット」をOFFにする。

原因②LINE_CHANNEL_SECRETが誤っている場合、署名検証に失敗し401エラーになる。

対策②npx wrangler tail --format jsonでresponse.statusを確認し、401であればシークレットを再設定（npx wrangler secret put LINE_CHANNEL_SECRET）。

リッチメニューが更新されない／表示が消える

症状新しい画像で登録し直したのに、トーク画面に古いものが表示され続ける。トーク画面を開き直しても内容が古いまま、あるいは一時的に非表示になる。

原因LINEアプリ・LINEプラットフォーム側のキャッシュ。または新しいrichmenuIdをdefaultに設定する前後の一瞬に旧メニューが削除されている。

対策トーク画面を一度閉じて開き直す。それでも変わらない場合は数分待つ（LINE側のキャッシュ反映待ち）。/admin/setup_richmenu実行時は「新規作成→アップロード→default設定→旧メニュー削除」の順で行い、default未設定の空白時間を作らない。

D1マイグレーションが "not authorized: SQLITE_AUTH" で失敗する

症状wrangler d1 migrations apply実行時にSQLITE_AUTHエラー。

原因D1はクライアントからのPRAGMA foreign_keys変更とCREATE TEMP TABLEを許可しない。

対策マイグレーションSQLからPRAGMA文を削除し、一時テーブルを使わない手順（新テーブルへ直接コピー→旧テーブル縮小）に書き換える。

友だち追加イベントでBotが応答しない（DB書き込みエラー）

症状followイベント処理中にWorkerが例外を投げる。

原因INSERT文が、マイグレーションで既に削除されたカラム（例：role）を参照している。スキーマ変更時にコード側のSQL文を更新し忘れると発生する。

対策スキーマ変更（マイグレーション追加・カラム削除）を行った際は、該当テーブルへの全INSERT/UPDATE文をコード全体で検索し、整合性を確認する。node:sqliteを使ったローカル実行テストで検出可能。

返信が届かない・二重送信される

症状reply tokenの期限切れ、またはLINE側の再送信により同じ処理が二重実行される。

対策reply失敗時はpush APIへフォールバック。DB更新は必ずidempotency_keyで冪等化し、同一イベントの再処理では二重書き込みしない。

共通の心構え：後戻りできない操作（本番D1へのdestructiveなマイグレーション、richmenuの一括削除、シークレットの上書きなど）を行う前には、必ず現状のバックアップまたはロールバック手順を確認してから実行する。
